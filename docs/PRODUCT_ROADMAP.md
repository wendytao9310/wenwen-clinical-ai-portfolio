# Clinical AI Evidence & Safety Lab — 开源产品路线图

## 产品目标

构建一个面向临床 AI 产品团队的开源证据与安全工作台：输入产品 intended use、目标用户、任务、数据、模型输出与潜在伤害，输出可追溯的证据等级、安全等级、验证缺口、人工升级条件和测试计划。

首版不是诊断工具，不接收真实患者数据，不输出个体医疗建议，也不声称临床有效。

## 两条核心主线

### 1. Evidence awareness

- 每条产品主张绑定证据来源、样本、数据切分、目标人群和验证状态。
- 区分内部性能、外部验证、静默测试、前瞻性工作流评估和临床结局。
- 强制记录时间漂移、participant-held-out、site-held-out、校准、亚组和失败案例。
- 允许明确输出 `UNKNOWN`、`NOT VALIDATED` 和 `VERIFY BEFORE USE`。

### 2. Safety level

- L0：内容展示，不参与健康判断。
- L1：教育与信息整理，不产生个体化医疗建议。
- L2：低风险工作流辅助，必须允许用户检查和撤回。
- L3：临床决策支持，输出必须可追溯且由合格人员复核。
- L4：可能影响诊疗路径的高风险功能，需要前瞻性验证、治理与持续监测。
- L5：自动诊断、治疗或紧急处置；MVP 禁止实现，仅作为升级与监管边界标记。

以上是产品原型的风险分层，不是法规分类或监管结论。

## MVP

1. Intended-use builder：定义用户、场景、输入、输出、使用者和禁止用途。
2. Evidence card：记录数据来源、验证设计、结果、限制和证据等级。
3. Safety gate：根据潜在伤害、自动化程度和人工监督生成 L0–L5 建议。
4. Evaluation plan：生成合成数据测试、Bad Case、专家审查和可用性测试清单。
5. Feedback ledger：记录反馈者角色、场景、问题严重度、修改决定和版本。
6. Claim checker：检查 README、Demo 和网站是否把计划、内部测试或投稿误写成临床结论。

## 公开 Demo 的数据与伦理边界

- 仅使用合成病例、公开许可样例或去标识后的虚构场景。
- 不上传电子病历、原始访谈、语音、影像、EEG、生物样本或任何可识别数据。
- 不招募患者进行医疗建议测试；早期反馈只评估可理解性、流程和界面。
- 涉及患者或临床人员的正式研究，在开始前需要机构伦理与数据治理判断。

## 用户反馈设计

### 第一轮：5–8 名专业用户

目标角色：临床医生、临床研究者、医疗产品经理、数据科学家和质量/合规人员。

任务：为一个合成临床 AI 场景完成 intended use、证据卡和安全门槛，并使用 think-aloud 描述困惑点。

指标：任务完成率、完成时间、关键错误、SUS、信任校准问题、最严重安全缺口和建议优先级。

### 第二轮：公众/患者代表

仅测试风险说明、同意语言、数据用途和退出机制是否易理解，不让参与者依赖 Demo 做真实健康决策。正式招募前先获得伦理与机构要求判断。

## 迭代记录

每次发布保留：版本号、假设、测试对象、测试数据、已发现问题、修复、未解决风险和下一阶段准入条件。公开反馈使用 GitHub Issues 模板，避免提交任何健康或身份信息。

## 参考框架

- FDA / IMDRF Good Machine Learning Practice：强调全生命周期、代表性数据、人机团队和临床相关条件下的测试。
- DECIDE-AI：适用于 AI 决策支持系统早期、真实临床环境中的评估与报告。
- CONSORT-AI / SPIRIT-AI：适用于后续正式试验协议和临床试验报告，不应被 MVP 阶段提前声称满足。
- GitHub Pages 官方 Actions 部署模型：构建、上传 artifact、使用 OIDC 部署到 `github-pages` 环境。
